## 0806: Airflow ETL 구조 개선과 안정성 검증 회고

### 진행 내용
- **Airflow ETL 구조 개선:** 서울 공공자전거 ETL 코드를 수집, 정제·집계, 저장 영역으로 나누어 역할을 명확히 하였다.
- **안정성 보강:** API 페이지네이션과 재시도, MySQL 트랜잭션, 데이터 품질 검사를 정리하였다.
- **DAG 실행 검증:** Docker Compose 환경에서 Airflow DAG를 실행하고 전체 태스크의 동작을 확인하였다.

---

### 오늘 배운 내용
오늘은 서울 공공자전거 데이터를 수집하는 Airflow 과제를 다듬었다. 하나의 큰 파일에 기능을 모으기보다 수집, 정제·집계, 저장 단계로 코드를 나누니 DAG의 각 태스크가 어떤 책임을 가지는지 이해하기 쉬워졌다.

API 호출은 언제든 실패할 수 있으므로 타임아웃과 재시도가 필요하고, 중간 파일과 MySQL 결과는 같은 기간을 다시 실행해도 중복되지 않아야 한다는 점도 확인하였다. 단순히 한 번 성공하는 파이프라인보다 실패 후 다시 실행할 수 있는 파이프라인을 만드는 것이 중요하다는 것을 배웠다.

---

### KPT 회고

#### **Keep - 유지할 점**
코드를 작성하는 데서 끝내지 않고 실제 Airflow 환경에서 DAG를 반복 실행하며 태스크별 로그와 결과를 확인한 점은 유지하고 싶다. 오류가 발생한 위치를 찾아 구조까지 개선한 과정도 좋았다.

#### **Problem - 문제점**
초기 구현에서는 수집과 변환, 저장 로직이 큰 모듈에 함께 있어 수정 범위가 넓고 오류의 원인을 찾기 어려웠다. API 실패와 재실행 상황도 처음부터 충분히 고려하지 못했다.

#### **Try - 시도할 점**
앞으로는 파이프라인을 만들기 전에 단계별 책임과 입출력 계약을 먼저 정리하겠다. 정상 실행뿐 아니라 네트워크 실패, 잘못된 데이터, 중복 실행 상황도 함께 검증하겠다.

---

### 이번 주 개선 목표
- **ETL 책임 분리하기:** 수집, 처리, 저장 단계의 역할과 입출력을 명확히 정의한다.
- **실패 상황 고려하기:** API 재시도와 DB 롤백 등 복구 방법을 구현 전에 정리한다.
- **멱등성 확인하기:** 같은 기간을 반복 실행해도 중간 파일과 최종 결과가 중복되지 않는지 확인한다.
- **Airflow 로그 활용하기:** 태스크별 로그를 통해 실패 지점과 데이터 처리 건수를 점검한다.
