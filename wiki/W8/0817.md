## 0817: 월별 운행 원천과 기사 운행 이력 파이프라인 구축 회고

### 진행 내용
- **가짜 원천 데이터 구축:** 월별 기사·운행 데이터를 생성하는 API와 릴리스 DAG를 추가하였다.
- **수집 경로 전환:** HVFHV 운행 데이터와 기사 데이터를 새로운 원천 API에서 수집하도록 변경하였다.
- **Clean Silver 구축:** 두 데이터의 Bronze·Silver 처리 흐름을 만들고 계약 기간을 기준으로 기사와 운행 이력을 결합하였다.
- **스키마 정리:** HVFHV와 기사 운행 이력의 스키마 소유권을 중앙화하고 불필요한 Gold 계보 컬럼을 제거하였다.

---

### 오늘 배운 내용
오늘은 외부에서 바로 사용할 수 있는 원천이 부족한 상황에서 월별 가짜 기사·운행 데이터를 생성하고, 이를 실제 수집 파이프라인과 같은 계약으로 제공하는 흐름을 만들었다. 단순히 파일을 만드는 데서 끝내지 않고 API 공개, 릴리스 DAG, Bronze와 Silver 적재까지 연결하면서 원천 데이터도 하나의 운영 대상이라는 점을 배웠다.

기사와 운행 이력을 결합할 때는 기사 ID만으로 조인하면 안 되고 계약 시작일과 종료일 사이에 발생한 운행인지 확인해야 했다. 시간 범위를 포함한 조인은 데이터의 의미를 보존하기 위한 핵심 조건이었고, 여러 계층에서 같은 스키마를 따로 정의하지 않도록 중앙 스키마를 두는 것도 변경 누락을 줄이는 데 도움이 되었다.

---

### KPT 회고

#### **Keep - 유지할 점**
가짜 데이터라도 실제 운영과 같은 API·DAG·계층 구조를 거치도록 만든 점은 유지하고 싶다. 조인 전에 계약 기간과 스키마 소유권을 명확히 정의한 것도 좋았다.

#### **Problem - 문제점**
초기 Bronze 스키마가 API가 실제로 내려주는 파일과 달랐고, 월별 데이터 적재 계약에도 불필요한 정보가 섞여 있었다. 계층마다 스키마를 따로 관리하면서 수정 범위가 커지는 문제도 있었다.

#### **Try - 시도할 점**
원천 API의 실제 응답을 계약 테스트로 먼저 확인하고, 스키마는 한 곳에서 소유하도록 하겠다. 기간 조인에는 경계 날짜와 계약이 겹치는 경우를 포함한 테스트를 추가하겠다.

---

### 이번 주 개선 목표
- **원천 계약 검증하기:** API 응답과 Bronze 스키마가 일치하는지 자동으로 확인한다.
- **시간 조건 명시하기:** 기간 조인의 포함 범위와 경계값을 테스트로 남긴다.
- **스키마 소유권 통일하기:** 공통 스키마를 중앙에서 관리하고 중복 정의를 줄인다.
- **가짜 데이터도 운영처럼 다루기:** 생성, 공개와 적재 흐름을 재현 가능하게 유지한다.
