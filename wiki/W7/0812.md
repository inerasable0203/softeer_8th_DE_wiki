## 0812: 데이터 레이크 설계 결정과 Great Expectations 적용 회고

### 진행 내용
- **인프라 선택:** Airflow를 ECS Fargate보다 EC2에서 운영하기로 결정하였다.
- **테이블 포맷 검토:** 스키마 변경과 백필, 과거 버전 추적을 고려해 Iceberg 도입 근거를 정리하였다.
- **파티셔닝 기준 수립:** S3 경로에는 Hive Style Partitioning을 적용하되 데이터 크기와 사용 방식을 고려하기로 하였다.
- **데이터 검증 개선:** Gas·EV의 Bronze와 Silver 검증을 Great Expectations 기반으로 전환하였다.

---

### 오늘 배운 내용
오늘은 기술을 사용할 수 있다는 이유만으로 선택하지 않고 현재 프로젝트의 규모와 운영 조건에 맞는지 비교하였다. Airflow DAG 수가 적고 장애 대응 시간이 비교적 넉넉하며 수집 주기도 길기 때문에, 복잡한 ECS 구성보다 EC2가 적절하다고 판단하였다.

Iceberg는 현재 기능에 꼭 필요한 것은 아니지만 스키마와 파티션 방식이 바뀔 가능성, 과거 계산 결과 추적과 백필을 고려해 도입 근거를 정리하였다. 동시에 작은 일별 데이터까지 무조건 세밀하게 파티셔닝하면 오히려 작은 파일 문제가 생길 수 있으므로 데이터 특성에 따라 적용 범위를 정해야 한다는 점도 배웠다.

---

### KPT 회고

#### **Keep - 유지할 점**
EC2와 ECS, 일반 Parquet과 Iceberg의 장단점을 비교하고 선택 근거를 문서로 남긴 점은 유지하고 싶다. 데이터 품질 검사를 Great Expectations로 통일하려고 시도한 점도 좋았다.

#### **Problem - 문제점**
확장성을 생각하다 보면 현재 규모에 비해 복잡한 기술을 도입할 위험이 있다. 반대로 단순함만 추구하면 스키마 변경과 재처리 요구에 대응하기 어려울 수 있어 기준을 정하기가 쉽지 않았다.

#### **Try - 시도할 점**
기술을 도입할 때 현재 필요한 기능과 미래에 대비하는 기능을 구분하고 비용을 함께 적겠다. 파티션은 관습적으로 적용하지 않고 데이터 크기, 조회 조건과 파일 수를 확인한 뒤 결정하겠다.

---

### 이번 주 개선 목표
- **기술 선택 근거 남기기:** 필요성, 운영 비용과 기각한 대안을 함께 기록한다.
- **오버엔지니어링 점검하기:** 현재 요구사항에 비해 복잡도가 지나치게 커지지 않는지 확인한다.
- **파티션 전략 검증하기:** 데이터 크기와 조회 패턴을 기준으로 파티션 컬럼을 선택한다.
- **데이터 검증 표준화하기:** 반복되는 품질 검사를 Great Expectations 규칙으로 통합한다.
