## 0824: 원격 Lambda 실행과 완료 마커 기반 데이터 공개 회고

### 진행 내용
- **원격 실행 전환:** Airflow의 Lambda 호출 방식을 통일하고 Main DAG의 작업을 실제 AWS Lambda 원격 호출로 전환하였다.
- **완료 마커 도입:** 파일 생성과 데이터 공개를 분리하고 완료 마커가 있는 결과만 후속 단계에서 사용하도록 하였다.
- **입력 검증 강화:** 운영 Gold 실행 전에 필요한 Silver 파티션과 연료비 대상 월을 확인하도록 하였다.
- **Gold 배정 복구:** 월별 보고서 중심 모델을 재고 테이블로 바꾸고 재고 기반 기사별 차량 배정을 복구하였다.

---

### 오늘 배운 내용
오늘은 Airflow 프로세스 안에서 직접 처리하던 일부 로직을 AWS Lambda 원격 호출로 전환하였다. Airflow는 실행 순서와 상태를 관리하고 Lambda는 실제 수집과 변환을 수행하도록 역할을 나누면서, 호출 규격과 실패 응답을 공통화하는 것이 중요했다.

S3에 파일이 보인다는 사실만으로 정상 데이터라고 판단하면 작성 중이거나 일부만 생성된 결과를 읽을 수 있었다. 실제 데이터 파일을 모두 쓴 뒤 완료 마커를 마지막에 생성하고, 후속 작업은 이 마커를 기준으로 데이터를 공개하도록 바꾸었다. 또한 퇴사 기사를 Silver에서 제외하고 실제 재고를 기준으로 Gold를 배정하면서 기술적 완결성과 비즈니스 정합성을 함께 점검하였다.

---

### KPT 회고

#### **Keep - 유지할 점**
Airflow와 Lambda의 책임을 나누고 원격 호출 방식을 공통화한 점은 유지하고 싶다. 완료 마커를 통해 파일 생성과 공개 시점을 구분한 것도 좋았다.

#### **Problem - 문제점**
로컬 호출과 원격 호출이 섞이면서 DAG마다 응답 처리 방식이 달랐다. 완료되지 않은 파티션이 Gold 입력으로 선택되거나 대상 월이 다른 연료비가 연결될 가능성도 있었다.

#### **Try - 시도할 점**
원격 작업은 공통 호출기와 동일한 성공·실패 계약을 사용하겠다. 후속 Job은 완료 마커, 대상 월과 서비스 지역을 모두 확인한 뒤 입력을 선택하도록 하겠다.

---

### 이번 주 개선 목표
- **오케스트레이션 책임 분리하기:** Airflow는 제어를, Lambda와 Spark는 데이터 처리를 담당하게 한다.
- **완료된 데이터만 공개하기:** 완료 마커가 생성된 파티션만 후속 입력으로 사용한다.
- **입력 계보 확인하기:** 버전, 대상 월과 지역이 일치하는 데이터만 결합한다.
- **운영 규칙 반영하기:** 퇴사 기사와 실제 차량 재고 같은 비즈니스 조건을 품질 검증에 포함한다.
