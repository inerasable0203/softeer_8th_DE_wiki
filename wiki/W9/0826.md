## 0826: Gold 재처리 안전성과 전체 행 품질 검증 회고

### 진행 내용
- **재처리 안정성 강화:** 과거 Gold 백필이 최신 freshness를 갱신하지 않도록 실행 시각과 대상 시각을 분리하였다.
- **전체 행 GX 적용:** 표본이나 파일 존재 여부를 넘어 실제 데이터 행을 Great Expectations로 검증하였다.
- **월별 운행 검증 발행:** Spark가 Monthly Taxi Trip의 GX 결과를 생성하고 후속 단계가 활용할 수 있도록 하였다.
- **운영 문서 현행화:** 설정값을 분리하고 데이터 규모·계보와 파이프라인 운영 및 안정성 문서를 현재 코드에 맞게 정리하였다.

---

### 오늘 배운 내용
오늘은 과거 데이터를 다시 만드는 백필과 최신 데이터의 신선도를 갱신하는 작업이 같은 의미가 아니라는 점을 다루었다. 백필이 성공했다는 이유로 최신 freshness가 과거 시점으로 바뀌면 모니터링과 대시보드가 잘못된 상태를 보여줄 수 있었다. 논리적 대상 시각과 실제 실행 시각을 분리해 상태를 관리하였다.

품질 검증도 메타데이터와 일부 샘플 확인에서 실제 전체 레코드 검사로 확장하였다. Spark가 검증 결과를 만들어 전달하게 하면서 대용량 처리 환경에서 품질 검사를 어디서 수행하고 어떤 결과 계약을 남길지 고민하였다. 코드에 흩어진 설정을 분리하고 운영·계보 문서를 현행화하면서 구현과 문서가 같은 시스템을 설명해야 한다는 점도 느꼈다.

---

### KPT 회고

#### **Keep - 유지할 점**
백필, 최신 실행과 freshness의 의미를 분리한 점은 유지하고 싶다. 품질 검사를 실제 전체 행에 적용하고 결과를 후속 작업에 전달한 것도 좋았다.

#### **Problem - 문제점**
실행 시각 하나로 여러 상태를 표현하면 과거 재처리가 최신 상태를 덮어쓸 수 있었다. GX 실행 책임과 결과 전달 방식이 파이프라인마다 달라 공통 운영이 어려웠다.

#### **Try - 시도할 점**
데이터 대상 시각, 수집 시각과 실행 시각을 구분해 메타데이터 계약에 명시하겠다. GX 결과 형식을 통일하고 검증 비용과 실패율도 함께 관찰하겠다.

---

### 이번 주 개선 목표
- **백필과 최신 상태 분리하기:** 과거 재처리가 freshness와 최신 버전을 잘못 갱신하지 않게 한다.
- **전체 행 품질 검증하기:** 핵심 Silver 데이터는 실제 레코드 기준으로 검사한다.
- **GX 결과 계약 통일하기:** Spark와 Airflow가 같은 형식으로 검증 결과를 주고받게 한다.
- **문서와 코드 동기화하기:** 데이터 계보, 운영 절차와 설정 설명을 현재 구현과 맞춘다.
